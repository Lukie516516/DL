本文记录从已合并的 `feat/deal-library-split-deployment` 更新之后，到当前 `codex/deal-split-credit-system` 分支为止的主要新增能力、接口变化、部署接线和前端注意事项。

覆盖范围：

- 币币新模板 `DealOpenTokenToken`
- 前端与索引接口优化
- Deal 合约拆分与体积放松
- 官方 `DealInfoNFT` 信用分体系
- 合约边界限制与部署脚本更新

| 模块 | 本次变化 | 影响对象 |

## 2. 币币新模板 `DealOpenTokenToken`

### 2.1 使用场景

`DealOpenTokenToken` 是专门给开放式币币交易使用的轻量模板。

适用条件：

```text
templateType = TokenToToken
joinMode = Open
openTokenTokenFast = true
无商品 NFT 交割
无 NftGated
```

前端仍然调用 `DealFactory.createDeal`，只是在 `InitParams` 里打开：

```text
openTokenTokenFast: true
```

Factory 创建成功后会 emit：

```solidity
event DealOpenTokenTokenCreated(address indexed deal);
```

前端可以通过这个事件判断该 deal clone 是 `DealOpenTokenToken` 模板。

### 2.2 关键流程

`DealOpenTokenToken` 支持：

- A 在 `Ready` 阶段先付款。
- A 创建时可以传 `aNftId` 绑定官方 `DealInfoNFT`，成交后 A/B 都按信用体系记账。
- A 可以调用 `preAccept()` 预同意。
- B 加入后完成付款，进入 Locked/结算流程。
- B 加入后记录 `bJoinedAt`，Active 顶替等待窗口直接使用该 deal 的 `timeoutSeconds`。
- 如果 B 长时间不推进到 `Locked`，外部新用户可以调用 `replaceInactiveBAndJoin(optId, trackMe)` 顶替 B；旧 B 的资金和 InfoNFT 会退回/解锁，A 已经预付的资产保留。
- Locked 下 B 单方 Reject 时，在特定条件下会被清出，deal 回到 `Ready`。
- B 因退出、被 A 踢、超时被替换、或 Reject 被清退后，会记录为 `lastRemovedB`；该地址不能自己立刻重新 join，除非 A 重新 `openJoinFor(lastRemovedB)`。

新增事件：

```solidity
event APreAccepted(address indexed a_, uint64 at);
event BExpelledOnReject(address indexed prevB, uint64 when);
```

### 2.3 前端注意

- 这个模板仍然是币币交易，不是 swap/orderbook 交易。
- 只在 `TokenToToken` 下允许 `openTokenTokenFast`，其他模板打开会 revert。
- 如果创建者要参与信用分和 C 位候选，创建时传自己的官方 `DealInfoNFT tokenId` 到 `aNftId`；不传则 A 不加信用。
- 前端 ABI 要根据 `DealOpenTokenToken` ABI 读取 `preAccept`、`replaceInactiveBAndJoin`、`APreAccepted`、`BExpelledOnReject`。

## 3. Deal 合约拆分与体积放松

### 3.1 拆分前后

旧结构：

```text
DealFactory
  -> Deal
  -> DealOpenTokenToken
```

当前结构：

```text
DealFactory
  -> DealImplementationRegistry
       -> Deal
       -> DealNoAsset
       -> DealAAssetNft
       -> DealBAssetNft
       -> DealAAssetNftOnly
       -> DealBAssetNftOnly
       -> DealOpenTokenToken
  -> DealActivityIndex
  -> DealCreditGraph
  -> DealMessageHub
```

### 3.2 各实现合约职责

| 合约 | 用途 |
| --- | --- |
| `Deal` | ABI 兼容 fallback shell，保留公开字段和接口形状 |
| `DealNoAsset` | `TokenToToken / TokenToEmpty / EmptyToEmpty` |
| `DealAAssetNft` | A 方交付商品 NFT 的 `TokenToNft` |
| `DealBAssetNft` | B 方交付商品 NFT 的 `TokenToNft` |
| `DealAAssetNftOnly` | A 方交付商品 NFT 的 `NftToEmpty` |
| `DealBAssetNftOnly` | B 方交付商品 NFT 的 `NftToEmpty` |
| `DealOpenTokenToken` | `openTokenTokenFast` 专用币币模板 |

### 3.3 路由方式

`DealFactory` 不再直接保存每个模板实现地址，而是通过：

```solidity
DealImplementationRegistry.resolveImplementation(
    templateType,
    openTokenTokenFast,
    aAssetNftId,
    bAssetNftId
)
```

返回需要 clone 的 implementation。

### 3.4 当前体积

当前 `forge build --sizes` 关键结果：

| 合约 | Runtime Size |
| --- | ---: |
| `DealFactory` | `22,298 B` |
| `DealImplementationRegistry` | `1,503 B` |
| `DealNoAsset` | `21,690 B` |
| `DealOpenTokenToken` | `23,792 B` |
| `DealAAssetNft` | `23,124 B` |
| `DealBAssetNft` | `23,113 B` |
| `DealAAssetNftOnly` | `19,126 B` |
| `DealBAssetNftOnly` | `19,115 B` |

`DealFactory` 距离 24KB 上限约有 `2,278 B` 余量；`DealOpenTokenToken` 距离上限约有 `784 B` 余量。

### 3.5 后续开发建议

后续新增模板时，优先新增独立 implementation，再通过 registry 接入，避免继续把逻辑塞回 `DealFactory` 或单个 `Deal` 实现里。

## 4. 信用分体系

### 4.1 核心原则

当前信用体系只认官方 `DealInfoNFT`。

```text
信用绑定 tokenId，不绑定钱包地址。
官方 DealInfoNFT 可以转移，信用也随 tokenId 转移。
外部 NFT 不接入信用分体系。
```

V1 不做单独关系分，也不做信用衰减。

### 4.2 信用分来源

V1 信用分唯一来源：

```text
成功完成 P2P deal
```

不会因为以下行为直接产生信用分：

- 创建 deal
- 失败 deal
- 取消 deal
- 免费消息
- swap/orderbook 交易
- 单纯持有 DL
- 外部 NFT 行为

### 4.3 交易信用计算

信用分基准来自本次成交产生的 recognized token 手续费 U 价值。

当前口径：

```text
基础信用分 = 本次手续费的 U 价值
1U 手续费贡献 = 1 信用分
```

然后根据双方信用差额外奖励：

```text
最终信用分 = 基础贡献分 + 额外奖励分
额外奖励分 = 基础贡献分 * 信用差系数
信用差系数 = 对方信用分 / 自己信用分
信用差系数限制在 0.01 到 2 之间
```

0 分处理：

| 自己信用 | 对方信用 | 额外奖励系数 |
| --- | --- | --- |
| 0 | 0 | 0 |
| 0 | > 0 | 2 |
| > 0 | 0 | 0 |
| > 0 | > 0 | `对方 / 自己`，限制在 `0.01 - 2` |

示例：

```text
A 信用 = 10000
B 信用 = 200
交易手续费 = 30U

A:
基础 = 30
额外系数 = 200 / 10000 = 0.02
额外 = 30 * 0.02 = 0.6
总增量 = 30.6

B:
基础 = 30
额外系数 = 10000 / 200 = 50，封顶为 2
额外 = 30 * 2 = 60
总增量 = 90
```

### 4.4 top5 信用快照

每个官方 NFT 维护自己交易过对象中的 top5 信用快照。

规则：

- 只有成功完成 deal 才刷新。
- 对方在别处涨分，不会自动刷新到我的 top5。
- 我再次和对方交易时，才会刷新对方在我这里的信用快照。
- 每个 NFT 最多维护 5 个 top 信用对象。

### 4.5 C 位奖励目标

C 位候选来自双方各自的信用网络：

```text
A 侧候选 = A 自己 + A top5 里信用快照最高的人
B 侧候选 = B 自己 + B top5 里信用快照最高的人

A 侧最高者 vs B 侧最高者
分高者成为 C
平局不出 C
```

当前 C 位奖励仍沿用现有 DL 增发机制，不从真实手续费中切分。

### 4.6 防刷规则

- 同 owner 持有的两个官方 NFT 互相交易：不加信用、不刷新 top5、不产生 C。
- 没有官方 NFT 的用户可以交易，但不加信用、不进入 top5、不参与 C。
- 非官方 NFT 不参与信用体系。

### 4.7 主要读接口

`DealCreditGraph`：

```solidity
creditScore(uint256 tokenId) -> uint256
topCreditPeers(uint256 tokenId) -> CreditPeer[5]
bestCandidateOf(uint256 tokenId) -> (candidateTokenId, candidateOwner, score)
resolveCRewardTarget(...) -> (cTokenId, cOwner)
```

主要事件：

```solidity
event DealCreditRecorded(...)
event CreditUpdated(uint256 indexed tokenId, uint256 delta, uint256 newCredit)
event TopCreditPeerUpdated(...)
```

## 5. 前端与索引接口优化

### 5.1 Factory active/completed deal 列表

`DealFactory` 仍保留原来的读接口，但数据实际由 `DealActivityIndex` 存储：

```solidity
trackedCount(address user)
getTracked(address user, uint256 offset, uint256 limit)
isTracked(address user, address deal)

completedCount(address user)
getCompleted(address user, uint256 offset, uint256 limit, bool newestFirst)
```

前端可以继续读 Factory，不需要直接读 `DealActivityIndex`。

### 5.2 DealReader 批量上限

`DealReader` 增加批量上限：

```text
MAX_BATCH = 100
```

影响接口：

```solidity
getDeals(address[] deals)
getDealsSlim(address[] deals)
getDealsPlus(address[] deals, address profileNft)
```

前端一次最多传 `100` 个 deal 地址。

### 5.3 消息接口

`DealMessageHub`：

```text
MAX_MESSAGE_BYTES = 1500
MAX_PAGE_SIZE = 100
```

限制：

- 空消息会 revert。
- 超过 `1500 bytes` 会 revert。
- 分页 limit 超过 `100` 时按 `100` 返回。

相关接口：

```solidity
postMessage(address deal, string content)
getMessages(address deal, uint256 offset, uint256 limit)
```

前端写普通 Deal / OpenTokenToken 留言时统一调用 `DealMessageHub.postMessage(deal, content)`，不再调用 Deal 实例本身。

### 5.4 域名市场分页

`DCDomainMarket` 新增游标分页接口：

```solidity
getPublicListingsPage(uint256 cursor, uint256 limit)
    -> (ListingView[] result, uint256 nextCursor, bool hasMore)

getP2PListingsForBuyerPage(address buyer, uint256 cursor, uint256 limit)
    -> (ListingView[] result, uint256 nextCursor, bool hasMore)
```

分页上限：

```text
MAX_PAGE_SIZE = 100
```

### 5.5 OrderBook 队列分页

`DealSwapOrderBook` 新增：

```solidity
getQueuePage(address pair, bool isSellDL, uint256 offset, uint256 limit)
    -> (uint256[] ids, uint256 head, uint256 total)
```

用于前端展示队列订单，不需要一次性拉完整队列。

### 5.6 InfoNFT 分页和 metadata 限制

`DealInfoNFT` 增加：

```text
tokensOfOwnerPage limit 最大 100
imageURI 最大 512 bytes
image MIME 最大 64 bytes
username 最大 64 bytes
userDetail 最大 1000 bytes
```

metadata 字段还会拒绝不安全字符，避免 JSON 拼接风险。

## 6. 边界限制与安全性补充

| 项目 | 当前限制 | 说明 |
| --- | --- | --- |
| deal title | `96 bytes` | Factory 创建前检查 |
| deal description | `1500 bytes` | 创建 deal 时上链，可为空；Factory 创建前检查 |
| timeoutSeconds | 最大 `1 day` | 防止用户误填导致资产长期卡在 Locked |
| DealReader batch | `100` | 防止 read 爆量 |
| DealMessageHub message | `1500 bytes` | 防止链上存储过大 |
| MessageHub page | `100` | 分页上限 |
| DomainHall message/note | `1500 bytes` | 域名大厅消息限制 |
| DomainMarket page | `100` | 域名市场分页上限 |
| OrderBook page | `100` | 队列分页上限 |
| InfoNFT metadata | 多字段长度限制 | 防止 metadata 无边界增长 |

前端需要同步做输入限制，避免用户在交易签名后才因为合约限制失败。

## 7. 部署与接线

### 7.1 一键升级命令

复用现有链上状态时，使用：

```bash
AGIKING_RPC_URL=https://rpc.agikingrpc.shop npm run deploy:agiking:deal-upgrade
```

该脚本会部署并接线：

- 新 `DealFactory`
- 各类 Deal implementation
- `DealImplementationRegistry`
- `DealActivityIndex`
- `DealCreditGraph`
- 新 `DealMessageHub`
- 新 `DCDomainSwap`
- 新 `DCDomainHall`
- `DL MINTER_ROLE`
- `DealInfoNFT.addFactory / setFactory`
- AUSD/USDT pair 映射
- DomainSwap / DomainHall 权限
- DCDomainRank reporter

### 7.2 完全新链部署

如果是空链全新部署：

```bash
AGIKING_RPC_URL=https://rpc.agikingrpc.shop npm run deploy:agiking
```

### 7.3 不建议随便重部署的状态合约

生产或需要保留历史状态时，以下合约应复用旧地址：

| 合约 | 原因 |
| --- | --- |
| `DealInfoNFT` | 官方 NFT、owner、metadata、lock、信用载体都在这里 |
| `DCDomain` | 域名 NFT 状态 |
| `DCDomainMarket` | 域名挂单状态 |
| `DCDomainRank` | 域名排行、广告、分数状态 |
| `DealSwapOrderBook` | 队列订单状态 |
| 旧 pair 合约 | AUSD/USDT 等交易对流动性 |

### 7.4 旧 deal clone

已创建的旧 deal clone 不会因为新实现部署自动升级。

影响：

- 新 Factory 创建的新 deal 走新模板体系。
- 老 deal 仍然按旧实现逻辑运行。
- 前端如果要展示历史 deal，需要保留对旧 Factory/旧 clone 的兼容。

## 8. 前端对接清单

### 8.1 地址配置

前端需要更新：

- `DealFactory`
- `DealReader`
- `DCDomainSwap`
- `DCDomainHall`
- `DealMessageHub`
- 如需展示信用分，增加 `DealCreditGraph`

### 8.2 输入限制

前端应限制：

```text
deal title <= 96 bytes
deal description <= 1500 bytes
message <= 1500 bytes
DealReader batch <= 100
messages page limit <= 100
domain market page limit <= 100
InfoNFT userDetail <= 1000 bytes
```

注意：这里是 bytes，不是字符数。中文、emoji 等会占多个 bytes。

### 8.3 创建 deal

普通模板仍然走：

```solidity
DealFactory.createDeal(CreateParams)
```

创建时交易描述使用：

```text
init.description
```

规则：

```text
可为空
最大 1500 bytes
会写入链上 storage，所以会增加创建 deal 的 gas
DealReader.getDeal(deal).description 可读
```

币币快速模板额外设置：

```text
init.openTokenTokenFast = true
init.aNftId = A 的官方 DealInfoNFT tokenId；没有则传 0
```

域名入口使用：

```solidity
DCDomainSwap.createDeal(...)
DCDomainHall.pickUserAndCreateDeal(...)
DCDomainHall.template23...
```

这些域名入口也同步开放 `description` 参数，位置放在 `title` 后面；不需要描述时传空字符串。

这些入口内部会通过 `DealFactory.createDealFor` 创建 deal。

### 8.4 信用分展示

推荐展示口径：

- NFT 当前信用分：`DealCreditGraph.creditScore(tokenId)`
- NFT top5 信用快照：`DealCreditGraph.topCreditPeers(tokenId)`
- 当前 C 位候选：`DealCreditGraph.bestCandidateOf(tokenId)`

信用分不是实时关系网全局同步，top5 是成功交易后的快照。

## 10. 后续注意事项

1. 后续新增模板时，优先新建独立 implementation，再接入 `DealImplementationRegistry`。
2. 不建议再把大量模板逻辑塞回 `DealFactory`。
3. 信用分体系 V1 只从成功 P2P deal 产出，暂不接 swap/orderbook。
4. 如果未来要改变信用公式，应优先升级/替换 `DealCreditGraph`，不要把信用状态直接写死在 `DealInfoNFT` 里。
5. 如果未来要从真实手续费切分给 C 位，需要另开手续费分账版本；当前 C 位奖励仍是 DL 增发。
