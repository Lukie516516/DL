# 事件时间与本次部署对接说明

面向前端、索引和部署同学。核心目标是：交易界面的系统提示都能直接从链上事件拿到发生时间，不再为个别事件额外查区块时间。

---

## 1. 这次事件时间改了什么

本次把终局事件也补上了时间字段：

```solidity
event Completed(CompletionReason reason, uint64 when);
event Canceled(uint64 when);
```

以前 `Completed` / `Canceled` 没有 `when`，前端需要用 log 所在区块的 `timestamp`。现在不需要了，交易进程类事件统一从事件参数里取时间。

前端建议统一处理：

```ts
const ts = event.args.when ?? event.args.at ?? event.args.timestamp;
```

说明：

- 普通 deal 进程事件用 `when`。
- OpenTokenToken 的 `APreAccepted` 用 `at`。
- 留言 `DealMessageHub.MessageStored` 用 `timestamp`。
- `DealFactory.DealRewardsLogged` 仍然是奖励汇总事件，本身不带 `when`，如需展示奖励发生时间，可用该 log 所在 block timestamp。

## 2. 交易界面 8 类系统提示对应事件

| 前端提示 | 链上事件 | 时间字段 | 关键字段 | 备注 |
| --- | --- | --- | --- | --- |
| `{用户名}已加入合约` | `Joined(b, nftLockedB, when)` / OpenTT `Joined(b, nftLocked, when)` | `when` | `b` | B 成功加入时发出 |
| `{用户名}已完成注金` | `Paid(payer, isPartyA, when)` | `when` | `payer`, `isPartyA` | A/B 注入资产成功后发出 |
| `{用户名}已撤金` | `WithdrawnInActive(payer, isPartyA, when)` | `when` | `payer`, `isPartyA` | Active 状态下撤回已注入资产 |
| `{用户名}已同意/拒绝交易` | `VoteCast(who, isPartyA, vote, when)` | `when` | `who`, `vote` | `vote=1` 同意，`vote=2` 拒绝 |
| `DEAL!!!` / `交易失败` | `Completed(reason, when)` / `Canceled(when)` | `when` | `reason` / 无地址字段 | 成交用 `Completed`；失败用 `Canceled`，谁导致失败需结合前面的 `VoteCast` / `ForcedAfterTimeout` |
| `{用户名}已超时` | `ForcedAfterTimeout(caller, completed, when)` | `when` | `caller`, `completed` | `completed=true` 表示超时成交，`false` 表示超时取消 |
| `{用户名}已被移除交易` | `ActivePartnerCleared(prevB, reason, when)` | `when` | `prevB`, `reason` | `reason=2` A 踢 B，`reason=3` 外部用户顶替 B |
| `{用户名}已退出交易` | `ActivePartnerCleared(prevB, reason=1, when)` | `when` | `prevB`, `reason` | B 自己退出 |

OpenTokenToken 还有一个特殊清退事件：

| 前端提示 | 链上事件 | 时间字段 | 说明 |
| --- | --- | --- | --- |
| `{用户名}已被移除交易` | `BExpelledOnReject(prevB, when)` | `when` | OpenTT 中 B 在 Locked 后拒绝，且 A 不是拒绝时，B 被清退，交易回到 Ready |

## 3. 常用枚举解释

### 3.1 `Vote`

```text
0 = Unset
1 = Accept
2 = Reject
```

前端文案：

- `vote = 1`：`{用户名}已同意交易`
- `vote = 2`：`{用户名}已拒绝交易`

### 3.2 `CompletionReason`

```text
0 = BothAccepted
1 = ForcedByA
2 = ForcedByB
```

前端可以先不细分展示，统一显示 `DEAL!!!`。如果要细分：

- `BothAccepted`：双方同意成交。
- `ForcedByA`：A 已同意，对方超时未投，A 强制成交。
- `ForcedByB`：B 已同意，对方超时未投，B 强制成交。

### 3.3 `ActivePartnerCleared.reason`

```text
1 = B 自己 exitByB 退出
2 = A 调 kickBByA 踢出 B
3 = OpenTT Active 阶段外部新用户 replaceInactiveBAndJoin 顶替旧 B
4 = OpenTT Locked 阶段 B 不确认，外部新用户 replaceNonVotingBAndJoin 顶替旧 B
```

前端文案建议：

- `reason = 1`：`{prevB}已退出交易`
- `reason = 2`：`{prevB}已被移除交易`
- `reason = 3`：`{prevB}已被顶替`

## 4. 留言事件和时间

普通 Deal / OpenTokenToken 留言统一走：

```solidity
DealMessageHub.postMessage(address deal, string content)
```

留言存储事件：

```solidity
event MessageStored(
    address indexed deal,
    address indexed sender,
    uint256 indexed index,
    uint64 timestamp
);
```

前端读取时间用 `timestamp`。

注意：

- 不再调用 `Deal.postMessage(...)`。
- Hub 会校验 `deal` 是 Factory 登记过的 deal。
- Hub 会校验 `msg.sender` 是当前 `a` 或 `b`。
- 留言费由 `DealFactory.chargeMessageFeeFrom(sender)` 统一执行。
- 如果开启留言收费，用户需要授权 `DealFactory` 消耗 DL。

## 6. 这次需要重新部署哪些

### 6.1 推荐方案：整套 Deal 入口重部署

测试期建议走这个方案，最不容易出现新旧 ABI 混用。

需要部署：

| 合约 | 是否必须 | 原因 |
| --- | --- | --- |
| `DealFactory` | 是 | `chargeMessageFeeFrom` 已允许 `DealMessageHub` 直接计费；新 Factory 也方便统一接线新实现 |
| `DealMessageHub` | 是 | 新增前端入口 `postMessage(deal, content)` |
| `Deal` implementation | 是 | ABI 里的 `Completed/Canceled` 已改为带 `when` |
| `DealNoAsset` implementation | 是 | `Completed/Canceled` 带 `when`，且已移除本体留言逻辑 |
| `DealAAssetNft` implementation | 是 | 同上 |
| `DealBAssetNft` implementation | 是 | 同上 |
| `DealAAssetNftOnly` implementation | 是 | 同上 |
| `DealBAssetNftOnly` implementation | 是 | 同上 |
| `DealOpenTokenToken` implementation | 是 | `Completed/Canceled` 带 `when`，OpenTT 顶替/信用/留言入口都在这里 |
| `DealImplementationRegistry` | 建议新部署 | 让新 Factory 指向这一批新 implementation |
| `DealActivityIndex` | 新 Factory 时必须新部署 | 构造参数绑定 Factory 地址 |
| `DealReader` | 如 ABI/读取结构需要最新产物则重部署 | 本次事件时间不是 Reader 负责；但前端通常随部署包更新 ABI |

通常可以复用：

| 合约 | 是否可复用 | 注意 |
| --- | --- | --- |
| `DCToken/DL` | 可复用 | 需要给新 Factory `MINTER_ROLE` |
| `AUSD/USDT` | 可复用 | 新 Factory 需要重新设置 recognized tokens |
| `DealInfoNFT` | 可复用 | 需要 `addFactory(newFactory)` / `setFactory(newFactory)`，否则新 deal 不能正常锁/记信用 |
| `DealCreditGraph` | 可复用 | 需要 `setRecorder(newFactory, true)` |
| `DealLib` | 可复用，如果没有改库 | 当前事件时间改动不需要重部署 `DealLib` |
| `DealAssetNftLib` | 可复用，如果没有改库 | 当前事件时间改动不需要重部署该库 |
| Pair / Router / OrderBook | 可复用 | 本次不是 swap/pair 逻辑变更 |

### 6.2 最小方案：不换 Factory，只升级实现和 Hub

如果不想换 Factory，也可以：

1. 部署新的 `DealMessageHub(oldFactory)`。
2. 在新接口 Factory 上用 `setServiceGlobals(newHub, 0, 0, 0, 0)` 更新 Hub；旧 Factory 版本才使用 `setGlobal("dealMessageHub", newHub)`。
3. 如果旧 Factory 的 `chargeMessageFeeFrom` 仍只允许 `isAllowedCreateFor[msg.sender]`，还要：

```solidity
DealFactory.setAllowedCreateFor(newHub, true)
```

4. 部署全部新的 Deal implementation。
5. 更新旧 Factory 的 implementation 指针 / registry。

这个方案的风险是：旧 Factory 版本、旧全局配置、旧授权状态容易混在一起。测试期不建议优先用。

## 7. 部署后需要怎么接线

新 Factory 需要完成这些配置：

```text
setCoreGlobals(DL, DealInfoNFT, WNATIVE, DealPairManager)
setServiceGlobals(DealMessageHub, DealCreditGraph, DealActivityIndex, DealResultIndex, DealImplementationRegistry)
setOpsGlobals(DealSwapOrderBook, DealNftGovernanceActivity, DCDomainRank)
setRecognizedTokens(AUSD, USDT)
DealPairManager.mapExistingPair(AUSD, pairDlAusd)
DealPairManager.mapExistingPair(USDT, pairDlUsdt)
setTreasuryByAdmin(treasury)
```

Registry 需要配置：

```text
Deal
DealNoAsset
DealAAssetNft
DealBAssetNft
DealAAssetNftOnly
DealBAssetNftOnly
DealOpenTokenToken
```

外部合约授权：

```text
DL.grantRole(MINTER_ROLE, newFactory)
DealInfoNFT.addFactory(newFactory)
DealInfoNFT.setFactory(newFactory)
DealCreditGraph.setRecorder(newFactory, true)
```

如果域名入口继续走新 Factory：

```text
重新部署或重新接线 DCDomainSwap / DCDomainHall 到 newFactory
newFactory.setAllowedCreateFor(DCDomainSwap, true)
newFactory.setAllowedCreateFor(DCDomainHall, true)
DCDomainRank.setDealReporter(DCDomainSwap, true)
DCDomainRank.setDealReporter(DCDomainHall, true)
DCDomainSwap.setReplaceTimeoutSeconds(120) // 可选；默认已经是 120 秒，允许 60 秒到 1 天
```

## 8. 前端需要更新哪些地址和 ABI

前端至少需要更新：

| 项目 | 原因 |
| --- | --- |
| `DealFactory` 地址 + ABI | 新创建 deal、奖励事件、全局读取 |
| `DealMessageHub` 地址 + ABI | 新留言入口和留言事件 |
| `Deal` / 各 implementation ABI | `Completed/Canceled` 事件签名变了 |
| `DealOpenTokenToken` ABI | OpenTT 事件和方法 |
| `DealReader` 地址 + ABI | 如果部署包里更新了 Reader |
| `DCDomainSwap` / `DCDomainHall` 地址 + ABI | 如果域名入口重新接到新 Factory |
| `DealCreditGraph` ABI | 展示信用分时需要 |

最重要的 ABI 变更：

```solidity
Completed(CompletionReason reason, uint64 when)
Canceled(uint64 when)
DealMessageHub.postMessage(address deal, string content)
DealMessageHub.MessageStored(address deal, address sender, uint256 index, uint64 timestamp)
```

## 9. 上线检查清单

部署后至少检查：

1. `DealFactory.dealMessageHub()` 返回新 Hub。
2. `DealMessageHub.factory()` 返回新 Factory。
3. 新 Factory 的 `dealImplementationRegistry` 已指向新 Registry。
4. 新 Registry 里的 7 个 implementation 都是本次新地址。
5. 新创建一笔普通 deal，完成后能收到 `Completed(reason, when)`。
6. 新创建一笔取消 deal，取消后能收到 `Canceled(when)`。
7. 新创建一笔 OpenTokenToken，B 加入、注金、投票、成交事件都有 `when`。
8. 前端调用 `DealMessageHub.postMessage(deal, content)` 可以写留言。
9. 如果留言收费开启，用户授权 `DealFactory` 后能正常 burn DL。
10. 前端不要再调用 `Deal.postMessage(...)`。

---

## 10. 给前端的一句话

交易进程事件现在基本统一成：事件里直接带时间。前端做时间线时优先取 `when`，OpenTT 预同意取 `at`，留言取 `timestamp`。普通交易留言改为调用 `DealMessageHub.postMessage(deal, content)`，不要再调 deal 实例的 `postMessage`。
